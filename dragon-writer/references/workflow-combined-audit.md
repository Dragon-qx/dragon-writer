# 模式 G：合并冷读

## 目的

让一个不了解创作计划的编辑连续阅读用户选定的章节，发现单章冷读不容易暴露的读者可见问题：章际跳接、前情复述、情节同构、关系体感突变、人物似乎无故知情、时间体验混乱、语言模式重复与节奏塌陷。

隐藏 canon、精确故事时钟、信息获知路径、关系权限、道具和钩子由主代理知情审计，不伪装成冷读。

## 触发时机

写作任务终点由主代理询问一次是否进入合并审核：

- 单章任务：该章封板后询问。
- 连续写作：只在最后一章封板后询问，中途不打断。
- 用户指定全部、部分或章节区间；用户跳过则结束。

## 纯正文审计包

审计包只能包含用户选定的章节正文，按阅读顺序排列，并使用中性分隔：

```bash
python scripts/build_cold_read_packet.py <book-dir> --final-range <START>:<END> --manifest story/runtime/combined-<START>-<END>.cold-source.json
```

```text
===== 第 N 章 =====
<标题与正文>

===== 第 N+1 章 =====
<标题与正文>
```

除正文和中性冷读规则外，禁止附带：

- 大纲、题材说明、作者意图、人物卡；
- 工作包、章节 intent、时间线、状态、信息链、关系账本；
- 钩子、数字锚点、情节指纹、近似文本脚本结果；
- 目标字数、怀疑点、预期发现、修改方向；
- 以前的审计报告、作者或主代理解释。

## 串行步骤

1. 主代理先运行知情跨章审计和 `check_chapter_overlap.py`，记录问题但不把结果传给冷读者。
2. 启动一个全新、不继承主代理对话的子代理；不得与写作或其他审计并行，不得复用之前的审计代理。
3. 使用 `workflow-continue.md` 的中性冷读提示词，只要求严重度、正文位置 / 短引、读者影响和修复方向。
4. 子代理只报告，不续写、不改写，也不裁决正文之外的事实。
5. 主代理结合完整项目状态修改正文。每个被改的已封板章先用 `chapter_txn.py ... reopen`，按章号串行重跑草稿哈希、字数 / Evidence Map、知情连续性、冷读和项目验证；不得把多个章交给并行写手。
6. 确有必要时最多复审一次；使用另一个全新子代理，只给修改后的纯正文，不给一审报告。
7. 未修复发现写入 `story/audit-drift.md`，注明章节范围。

## 与单章门禁的关系

- 合并冷读是任务终点的增量检查，不替代逐章机械门禁、主代理知情审计和单章冷读。
- 子代理只负责读者视角；主代理负责事实判定、所有正文修改和 Runtime 更新。
- 任何合并审核都不得启动多个子代理并行分章，否则会失去统一阅读顺序并重新引入跨章状态分裂。
