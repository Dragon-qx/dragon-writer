# 模式 G：合并审核（统一审计）

把用户选定的多章正文合并成一份文本，做一轮**完整 43 维**深化审计，重点暴露单章审计看不到的**跨章一致性问题**（时间线、设定冲突、伏笔兑现、信息越界、弧线 / 支线、跨章重复、去 AI 味等）。

## 触发时机

写作任务完成时主代理**必须主动询问用户**："是否进入合并审核？"，不得静默跳过提问。**仅在任务终点询问一次**：

- **单章写作**（只写一章）：该章落盘并通过单章审计之后询问。
- **连续创作**（一轮连续产出多章）：**只在最后一章完成后询问**，中途各章完成时不打断。

用户选择：

- **跳过**：本轮不合并审核。
- **进入并指定范围**：全部章节 / 部分章节（指定编号或区间）。

## 步骤

1. **询问用户**：是否进入合并审核？进入则确认范围（全部 / 部分 / 指定区间）。
2. **准备审计包**：合并选定章节正文为一份文档；附 43 维清单 + 最小连续性事实（主角身份、跨章时间线、空间锚点、活跃钩子、道具账本摘要——**不含**大纲、作者意图、角色档案、叙事目标）。
3. **子代理冷读审计**：启动独立子代理（新鲜读者视角，**非**起草上下文），对合并正文逐维审计，返回结构化报告（每维 pass / fail / unknown + 原文证据 + 建议 + 文风专项）。
4. **主代理按报告修改**：critical 必过；warning 修或留漂移记录；info 仅记录。
5. **留痕**：未当场修复的发现写入 `story/audit-drift.md`（注明跨章节范围）。
6. **可选复审**：改动面大时，重跑受影响维度及其依赖闭包。

## 与单章审计的关系

- **单章审计**：每章落盘前必过，看"章内问题"。
- **合并审核**：用户发起，看"跨章问题"，是**增量**，不替代单章审计。
- 两者都**只能由子代理**执行，主代理 / 起草上下文不得自评。
